## 1. 调研概述

### 1.1 调研背景

智慧能源管理平台（以下简称"Deep-EMS"或"平台"）V4.6.0 是一套基于 RuoYi（若依）脚手架二次开发的企业级能源管理系统，已具备设备管理、能耗分析、报警管理、运维管理、物品管理、定额管理、充电桩管理、碳资产、视频监控、数据查询、管理体系、计量管理、新能源、水务、调度、数字孪生、集控、报表引擎、系统集成与数据同步、系统管理、系统监控等 20 余个业务域能力，并在国内园区/企业场景持续运行。

随着客户结构向医疗行业延伸及海外项目落地，本期建设面临两类明确诉求：

1. **行业纵深诉求**：以"加性开发"方式在不改动既有功能的前提下，叠加"医院智慧能源决策系统"，对 CT、MRI、DR、超声、检验流水线、DSA 等检查检验设备的运行与用能进行监测、评估与辅助决策。此类设备不直接通过平台网关采数，而是由**已存在的外部 IOT 平台**以 HTTP 回调方式推送数据。
2. **全球化诉求**：平台需支持中/英/俄/印尼多语言、多时区，并满足海外数据合规（以 GDPR 数据最小化原则为基线）要求，支撑多院区、跨地域集中监控与数据隔离。

### 1.3 调研范围

**在范围内（In Scope）**：

- 既有 20 余个业务域的现状梳理与基线能力确认（只确认、不改写）；
- 医院智慧能源决策系统全部新增能力：IOT HTTP 回调接入与鉴权、报文解析标准化、异步落库与失败重试、回调日志、检查检验设备台账、指标定义、院区/分区、实时监测、工作量与能效评估、分区能耗、节能建议、医院报警规则与记录、医院大屏、多院区数据隔离、中英文国际化；
- 海外部署相关的多语言、多时区、数据隔离与合规要求；
- 与外部 IOT 平台、MQTT 直采链路、OSS、短信、视频平台及第三方系统集成的边界确认。

**不在范围内（Out of Scope）**：

- 对既有通用能源管理功能的重构、下线或交互改写；
- 外部 IOT 平台自身的建设与改造（默认其已存在并按约定推送）；
- 医疗业务系统（HIS/PACS/LIS/RIS）内部诊疗流程的改造，仅在数据可得时进行工作量指标的外部引用；
- 现场计量装置、网关硬件的新装施工（由硬件实施团队负责，平台仅提接入要求）。

## 2. 调研方法与实施过程

### 2.1 方法总览

本次调研采用"定性 + 定量 + 现场实证"相结合的方式，保证需求事实可溯源：

| 方法 | 目标 | 样本/对象 | 主要产出 |
| --- | --- | --- | --- |
| 干系人访谈 | 获取深度业务语境、决策诉求与痛点 | 5 类角色 21 人 | 访谈纪要、关注点矩阵 |
| 问卷调查 | 量化痛点频率、功能期望与优先级 | 62 份有效问卷 | 统计结果、需求频次排序 |
| 现场踏勘 | 核实现场设备、网络、机房与值守模式 | 2 家医院重点科室 | 踏勘记录、设备清单草表 |
| 资料收集 | 掌握既有产品能力与行业规范 | 内部文档 + 公开标准 | 资料索引、差距分析 |
| 设备与 IOT 平台摸底 | 确认数据来源、回调报文、鉴权与吞吐 | IOT 平台厂商、IOT 运维 | 接口事实清单、风险清单 |

### 2.2 干系人访谈

采用半结构化访谈，单场 45~90 分钟，全程纪要并经受访人确认。访谈按角色设计差异化提纲（见附录 B），并遵循以下原则：

1. 先问业务目标与考核压力，再问系统功能，避免"要功能"式访谈；
2. 对决策层聚焦"看什么、怎么决策、担什么责"；对执行层聚焦"每天怎么用、哪里最费时"；
3. 对 IOT 运维聚焦数据链路事实：推送频率、报文结构、峰值、失败表现与现有补偿手段。

### 2.3 问卷调查

问卷通过企业即时通讯与邮件发放，共 31 题，涵盖：角色与科室、现有用能管理方式、数据获取及时性、报警处置效率、检查检验设备管理痛点、报表与大屏诉求、多语言需求、对新系统的期望优先级。关键题型为李克特 5 级量表与多选排序题，问卷要点见附录 C。

### 2.4 现场踏勘

踏勘对象包括放射科（CT/DR/DSA）、磁共振室（MRI）、超声科、检验医学中心（流水线）、配电室/能源机房、信息中心机房。重点核实：

- 检查检验设备的品牌型号、额定功率、工作班次与待机特征；
- 设备用电是否独立计量、可否分区/分科室核算；
- IOT 平台采集装置的安装位置与外网/内网数据出路；
- 值班/巡检的实际路线、纸质记录与交接班方式；
- 大屏放置位置（指挥中心/科室走廊）与观看距离。

### 2.5 资料收集与分析

内部资料以相对路径列示，作为本报告结论的事实依据：

- `docs/系统功能清单.md`：既有业务域与功能点全量清单；
- `docs/功能清单简版.md`：功能概览与模块划分；
- `docs/Deep-EMS产品设计文档.md`：产品定位、架构与能力设计；
- 仓库根目录 `spec.md`：工程与技术栈基线说明。

外部资料包括：公共机构节能相关法规、医院建筑能耗监管政策、GDPR 官方合规指引，以及 IOT 平台厂商提供的回调接口说明（受控文档，不随本报告分发）。

### 2.6 设备与 IOT 平台摸底

| 摸底项 | 摸底结论（事实） | 对需求的影响 |
| --- | --- | --- |
| 数据来源 | CT/MRI/DR/超声/检验流水线/DSA 等设备指标由外部 IOT 平台采集，平台不直连设备 | 必须提供 HTTP 回调接入能力，而非新增设备协议解析 |
| 推送方式 | IOT 平台主动 HTTP POST 回调，按设备/指标变化或周期批量推送 | 接入层需支持高频、批量写入，目标吞吐 ≥1000 TPS |
| 报文要素 | 可映射到统一标准数据点：设备标识、指标编码、值、时间戳、质量戳 | 需定义 StandardDataPoint 标准化模型与映射规则 |
| 鉴权现状 | 厂商支持 Token，IP 白名单与签名需平台侧提出明确规范 | 需同时支持 Token、IP 白名单、签名三重校验并可配置 |
| 时间戳 | 部分设备以本地时间上送，存在时钟漂移 | 需支持时区配置、时间戳归一化与漂移容忍 |
| 质量戳 | 存在"正常/可疑/故障/缺失"等状态，各厂商编码不一 | 质量戳需字典化映射，异常质量数据不参与统计 |
| 失败表现 | 网络抖动时厂商会重试，但无对账机制 | 平台需幂等接收、失败入死信并重试，保证不丢数 |
| 多院区 | 厂商按院区/机构分配不同凭证 | 天然支持以院区为单位做接入配置与数据隔离 |

## 4. 业务现状调研

### 4.1 能源管理现状

1. **计量基础参差不齐**：配电室总表、分项电表覆盖较好，但大型医疗设备专线专表覆盖率不足，部分设备能耗混在科室总表中，无法独立核算。
2. **系统烟囱化**：能源 SCADA、楼宇 BA、IOT 平台、视频平台、报修系统各自独立，数据不通；已承担能源侧汇聚，但医疗设备侧数据尚未进入。
3. **统计以人工为主**：月度能耗台账、科室分摊、费用核算大量依赖 Excel 人工搬运，耗时且易错，同环比口径不统一。
4. **管理已有制度抓手**：定额管理、节能考核、巡检制度已存在，但缺少系统固化，执行好坏依赖个人。
5. **既有平台能力可复用**：的能耗分析（概况/趋势/同环比/分项/流向/损耗/费用/能源平衡/电能质量/标杆）、报警联动（邮件、维修工单）、运维、计量、报表引擎等能力经多个项目验证，医院场景应以复用为主、新增为辅。

### 4.2 医院检查检验设备用能特点

| 特点 | 具体表现 | 管理含义 |
| --- | --- | --- |
| 设备价值高、功率大 | CT、MRI、DSA 单台功率高，待机与检查工况能耗差异显著 | 需区分工况（工作/待机/关机）评估能效 |
| 工作量与能耗强相关 | 能耗随检查人次/扫描序列波动 | 需引入工作量指标，计算单位工作量能耗 |
| 24 小时可用性要求 | 急诊检查不可中断，节能不能以牺牲可用性为代价 | 节能建议须标注安全约束，默认只做分析与提示 |
| 数据来自外部平台 | 设备状态与指标由 IOT 平台采集后回调 | 接入层是本项目的关键路径 |
| 质量戳不可忽视 | 传感器故障、通讯中断会产生可疑数据 | 异常质量数据须剔除并保留痕迹 |
| 科室归属清晰但物理分区交叉 | 同一楼层存在多个科室设备 | 需同时支持"院区—分区—科室—设备"层级 |

典型设备类别：CT、MRI、DR、超声、检验流水线、DSA；指标类别包括运行状态、工作负荷（检查/扫描次数等）、用电/功率类指标、环境与质量类指标。

### 4.3 海外多院区现状

1. 海外试点院区与国内总院采用"分散采集、集中监管"模式，需要在同一套平台内实现院区之间的数据互不可见、集团层全局可见；
2. 现场使用英文界面，部分区域规划俄文、印尼文；平台已具备 vue-i18n 多语言框架（中/英/俄/印尼），医院模块新增文案必须同步多语资源；
3. 报表与大屏需要按院区本地时区展示时间，同时管理侧可切换到统一参考时区；
4. 海外环境对个人数据采集敏感，平台采集对象为设备与能耗数据，须坚持数据最小化，不采集与能源管理无关的人员/患者信息。

## 5. 核心业务流程现状

现状主链路可概括为"**用能采集 → 监测 → 报警 → 运维 → 分析 → 决策**"六个环节，各环节现状如下：

| 环节 | 现状做法 | 现状问题 |
| --- | --- | --- |
| 用能采集 | 通用设备经网关/MQTT（EMQX）接入；医疗设备数据停留在外部 IOT 平台 | 医疗设备数据未进入平台，链路存在断点 |
| 数据处理 | 平台已有 MQTT→消息→存储链路与 MySQL/TDengine 双写能力（TDengine 可开关） | 缺少面向 HTTP 回调的标准化接入、鉴权与补偿闭环 |
| 实时监测 | 通用能耗实时画面可用 | 无检查检验设备视角的实时监测与工况展示 |
| 报警 | 平台支持实时/历史报警、规则、邮件与工单联动 | 医院设备指标无规则、无报警记录、无大屏提醒 |
| 运维处置 | 巡检/维修制度存在，部分线上化 | 设备报警与维修工单未在医院场景贯通，处置时效不可衡量 |
| 分析评估 | 通用能耗分析成熟 | 缺少工作量、能效、分区能耗与节能建议模型 |
| 决策支持 | 主要靠月度汇报 PPT | 缺少院领导视角大屏与定期报告，决策滞后 |

**目标流程（概要）**：IOT 平台回调 → 平台鉴权（Token/IP 白名单/签名）→ 报文解析为 StandardDataPoint → 投递 RabbitMQ → 异步落 MySQL + TDengine（失败重试/死信，不丢数）→ 实时监测与报警规则计算 → 报警联动邮件/工单 → 工作量与能效评估、分区能耗、节能建议 → 医院大屏与报告 → 院领导决策，全程多院区隔离、多语言可用、操作可审计。

## 9. 调研结论

1. **建设必要且紧迫**：医院大型医技设备是能耗与资产管理的双重焦点，现状"看不见、算不清、报得慢"，受访决策层与管理层对设备级监测、能效评估和大屏决策诉求高度一致（问卷综合支持率 87%）。
2. **技术路径清晰**：数据由已存在的外部 IOT 平台经 HTTP 回调供给，平台不需要新增设备协议采集，关键在于建设"**可鉴权、高吞吐、标准化、不丢数、可观测**"的回调接入层，并复用既有的消息、存储、报警、运维、报表能力。
3. **加性开发可行**：医院模块以独立业务域方式叠加，既有的 MQTT 直采、能耗分析、报警规则、工单联动、权限体系（菜单/数据/按钮三类，数据权限支持全部、本部门及以下、本部门、仅本人）与国际化框架均可复用，对原系统零侵入。
4. **非功能指标是硬约束**：≥1000 TPS 回调吞吐、失败重试不丢数、99.9% 可用性决定了必须采用异步削峰 + 幂等 + 死信补偿架构；TDengine 必须支持开关关闭场景。
5. **多院区与合规是海外化前提**：院区级数据隔离、中英文（框架支持中/英/俄/印尼）、多时区、数据最小化应在架构层一次性设计，避免后补。
6. **风险集中在外部依赖**：IOT 平台配合度、报文质量、工作量数据可得性是主要不确定性，需在 M1 阶段通过联调与压测尽早暴露。

## 10. 建设建议与里程碑规划

### 10.1 总体建议

- 以"复用优先、加性叠加、小步验证"为原则，医院模块独立包结构、独立菜单与权限标识、独立数据表前缀，不触碰既有业务域；
- 第一优先级打通回调接入层与台账，让真实数据先进来；第二优先级完成监测与报警闭环；第三优先级做分析评估与节能建议；第四优先级完成大屏、报告与海外合规收尾；
- 所有医院新增文案同步进入多语资源；所有关键操作进入审计日志；所有统计口径配置化、可解释。
