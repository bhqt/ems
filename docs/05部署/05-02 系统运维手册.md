## 2 巡检制度

### 2.1 日常巡检（每日 1 次，建议 09:30；可与系统监控页核对）

| # | 巡检项 | 命令/入口 | 正常标准 |
|---|---|---|---|
| 1 | 主机资源 | `uptime`；`free -h`；`df -h`；`top -bn1 \| head -20` | load < CPU 核数；内存使用 < 80%；数据盘使用 < 85% |
| 2 | 容器状态 | `docker compose ps`（54：加 `-f docker-compose-54.yml`） | 全部 Up/healthy，无 Restarting |
| 3 | 后端服务 | `systemctl status zhurong-ems`；`curl -s http://localhost:8088/autoee-iot-ems/actuator/health` | active；`{"status":"UP"}` |
| 4 | Nginx | `systemctl status nginx`；`curl -I http://localhost/health` | 200/healthy（容器：`docker ps \| grep frontend`） |
| 5 | MySQL | `mysqladmin -uroot -p<pwd> ping`；`SHOW PROCESSLIST` 计数 | mysqld is alive；连接数 < max_connections 80% |
| 6 | Redis | `redis-cli -a <pwd> ping`；`info memory`、`info clients` | PONG；mem 未达 maxmemory；connected_clients 正常 |
| 7 | RabbitMQ | 管理台 Overview；`rabbitmq-diagnostics list_queues` | 无持续增长队列、消费者在线 |
| 8 | EMQX | Dashboard 统计/客户端数 | 设备在线数与基线偏差 < 20% |
| 9 | TDengine（启用时） | `taos -u root -p<pwd> -s "SHOW DATABASES;"`；磁盘 | 可连接；taos 数据盘 < 85% |
| 10 | 错误日志 | 后端 sys-error.log 当日 ERROR 条数 | 无新增 ERROR（或均为已知噪声） |
| 11 | 业务烟测 | 浏览器登录 → 设备列表 → 监测页 | 3 分钟内完成，数据为当日最新 |
| 12 | 备份结果 | 检查昨夜备份文件与大小、备份日志 | 文件存在、大小非 0、异机副本存在 |

### 2.2 每周/每月巡检

| 周期 | 项目 |
|---|---|
| 每周 | 慢 SQL TOP10 分析；RabbitMQ 死信/堆积历史；EMQX 认证失败审计；Nginx 5xx 比例；备份文件抽查恢复一次（备库实例） |
| 每月 | 全量恢复演练 1 次并出报告；账号清单复核（离职/僵尸账号）；证书有效期检查（<30 天发起更换）；容量趋势评估（磁盘/连接/消息量）；操作系统补丁评估；日志归档清理；灾备文档与密码信封更新 |

巡检记录留存不少于 6 个月；P1/P2 事件须输出事件报告（时间线、影响、根因、措施、防复发）。

## 3 服务启停与状态检查

### 3.1 Docker Compose 通用命令

```bash
cd <compose 所在目录>                 # 自研栈：/opt/zhurong-ems/compose；现网 54：54 脚本所在目录
docker compose ps                     # 查看服务状态/健康/端口
docker compose ps -a                  # 含已停止容器
docker compose logs -f --tail=200 <服务名>
docker compose top                    # 容器内进程
docker compose stats --no-stream      # 各容器 CPU/内存/IO 实时快照
docker compose restart <服务名>
docker compose up -d <服务名>         # 新建/启动单个服务
docker compose stop <服务名>
docker compose down                   # 停止并删除容器（卷保留，数据不丢）
```

54 现网在每条命令加 `-f docker-compose-54.yml`，例如：

```bash
docker compose -f docker-compose-54.yml ps
docker compose -f docker-compose-54.yml logs -f --tail=300 zhurong-ems-backend
docker compose -f docker-compose-54.yml restart zhurong-ems-backend
```

启动顺序：MySQL/Redis → RabbitMQ/EMQX/TDengine（healthy）→ 后端 → 前端。compose 已配置 `depends_on: condition: service_healthy` 时可直接整组 `up -d`。

### 3.2 后端（裸机 systemd）

```bash
systemctl start zhurong-ems
systemctl stop zhurong-ems
systemctl restart zhurong-ems
systemctl status zhurong-ems
journalctl -u zhurong-ems -f -n 300
ss -lntp | grep 8088
curl -s http://localhost:8088/autoee-iot-ems/actuator/health
```

优雅停止：先在 Nginx 摘流（注释 upstream 或权重置 0 并 reload），等待存量请求结束（最长 60s），再 stop。

### 3.3 Nginx

```bash
nginx -t                              # 配置校验（reload 前必须执行）
systemctl reload nginx                # 不停机重载
systemctl restart nginx
tail -f /var/log/nginx/ems_access.log /var/log/nginx/ems_error.log
# 容器：docker logs -f zhurong-ems-frontend；日志卷 .../zhurong-ems-frontend-logs
```

### 3.4 开机自启核对

```bash
systemctl is-enabled docker nginx zhurong-ems chronyd
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' zhurong-ems-mysql   # 应为 unless-stopped
```

## 4 中间件运维

### 4.1 MySQL 8.0.35（容器 zhurong-ems-mysql，库 autoee_ems，root/123456）

连接：

```bash
docker exec -it zhurong-ems-mysql mysql -uroot -p123456
mysql -h127.0.0.1 -P3306 -uems_app -p autoee_ems       # 应用账号（现网口令见密码信封）
```

常用运维语句：

```sql
SHOW GLOBAL STATUS LIKE 'Threads_connected';     -- 当前连接数
SHOW VARIABLES LIKE 'max_connections';           -- 上限（compose 启动参数 1000）
SHOW PROCESSLIST;                                -- 活动连接
-- 锁等待/长事务（8.0）
SELECT * FROM information_schema.innodb_trx ORDER BY trx_started LIMIT 10;
-- 库大小
SELECT table_schema, ROUND(SUM(data_length+index_length)/1024/1024,1) MB
FROM information_schema.tables GROUP BY table_schema;
-- 每张表大小 TOP20
SELECT table_name, engine, table_rows,
       ROUND((data_length+index_length)/1024/1024,1) MB
FROM information_schema.tables WHERE table_schema='autoee_ems'
ORDER BY data_length+index_length DESC LIMIT 20;
```

慢查询：

```sql
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';
SET GLOBAL slow_query_log=ON; SET GLOBAL long_query_time=2;   -- 临时开启
-- 分析：mysqldumpslow -s t -t 10 /var/lib/mysql/*-slow.log（容器内路径）
-- 或直接查 performance_schema.events_statements_summary_by_digest
```

注意事项：

- 逻辑删除约定：`del_flag`，0=存在、2=删除；查询/排障不要把已删数据当异常；
- 主键为雪花 ID（ASSIGN_ID），导出导入不要随意改为自增；
- 字符集统一 utf8mb4，新增库表必须显式指定，避免菜单/名称乱码；
- 禁止在生产直接执行无 WHERE 的 UPDATE/DELETE；数据修复 SQL 须经评审并在事务中预演（`BEGIN; ... ; SELECT 校验; ROLLBACK;`）。

### 4.2 Redis 7.2.3（容器 zhurong-ems-redis；shared 形态密码 difyai123456，后端默认 db13）

```bash
docker exec -it zhurong-ems-redis redis-cli -a <pwd>
# 容器未配密码时：docker exec -it zhurong-ems-redis redis-cli
127.0.0.1:6379> ping
127.0.0.1:6379> info memory        # used_memory / mem_fragmentation_ratio
127.0.0.1:6379> info clients       # connected_clients、blocked_clients
127.0.0.1:6379> info stats         # keyspace_hits/misses、evicted_keys
127.0.0.1:6379> info keyspace      # 各 db key 数（平台用 db13）
127.0.0.1:6379> config get maxmemory-policy
127.0.0.1:6379> dbsize
127.0.0.1:6379> slowlog get 10
127.0.0.1:6379> client list | wc -l
```

要点：

- **认证错误高发**：后端报 `WRONGPASS invalid username-password pair` 或 `NOAUTH` 时，核对三处一致——redis.conf `requirepass` / shared-redis 启动的 `--requirepass difyai123456`、后端 `spring.redis.password`、Redisson 单节点配置；
- 未设置 maxmemory 时依赖宿主机内存，建议设置上限并明确淘汰策略（缓存场景 `allkeys-lru`，平台无强持久依赖可开启 AOF 视情）；
- `evicted_keys` 持续增长说明内存吃紧；`mem_fragmentation_ratio > 1.5` 关注碎片（低峰重启可整理）；
- 缓存监控入口：平台内「系统监控 → 缓存监控」；在线用户在「系统监控 → 在线用户」。

### 4.3 RabbitMQ 3.12-management（容器 zhurong-ems-rabbitmq；管理台 15672）

```bash
docker exec zhurong-ems-rabbitmq rabbitmq-diagnostics ping
docker exec zhurong-ems-rabbitmq rabbitmqctl list_queues name messages messages_ready messages_unacknowledged consumers -p admin_vhost
docker exec zhurong-ems-rabbitmq rabbitmqctl list_connections name user vhost peer_host
docker exec zhurong-ems-rabbitmq rabbitmqctl list_exchanges -p admin_vhost | grep hospital
docker exec zhurong-ems-rabbitmq rabbitmqctl set_policy -p admin_vhost dlx '^hospital\.' '{"dead-letter-exchange":"hospital.topic.exchange"}'  # 按设计需要再设
```

管理台（http://IP:15672）重点页：Overview（速率）、Queues（messages ready/unacked、consumers）、Exchanges（`hospital.topic.exchange`）。平台链路：医院数据交换机 `hospital.topic.exchange` → 队列 `hospital.device.data.queue`，路由键 `hospital.device.data`。

判障要点：

- `messages_ready` 持续上涨且 consumers=0：后端消费者断开/未启动 → 检查后端日志与 MQ 账号/vhost；
- `messages_unacknowledged` 堆积：消费变慢或抛错 basicNack 重回队列 → 查后端 ERROR 与死信；
- vhost 错误（`NOT_ALLOWED - vhost admin_vhost not found`/access refused）：本地/现网用 `admin_vhost`，账号须为 `rabbitmq/rabbitmqpassword`（shared-infra）或现场 ems_mq 且已对该 vhost 授权；自研 compose 默认是 guest/guest、默认 vhost `/`，切环境必须同步配置；
- guest 只能 localhost 登录，远程连接必须自建用户。

### 4.4 EMQX 5.3.2（容器 zhurong-ems-emqx；Dashboard http://IP:18083，admin/public）

| 运维项 | 入口/命令 |
|---|---|
| Broker 状态 | `docker exec zhurong-ems-emqx emqx_ctl status` |
| 在线客户端 | Dashboard「监控 → 客户端」；`emqx ctl listeners` 看 1883 连接数 |
| 订阅关系 | Dashboard「监控 → 订阅」，确认后端服务客户端订阅 electric/#、water/# |
| 主题消息计数 | Dashboard「监控 → 主题监控」 |
| 认证失败 | Dashboard「问题诊断 → 日志」，搜 `authentication_failed` |
| 账号管理 | 访问控制 → 认证（Built-in DB）→ Users；授权规则按主题前缀 |
| 黑名单/踢线 | 访问控制 → 黑名单；客户端页可踢除异常连接 |
| 监听器 | 1883 TCP、8883 TLS、8081 WS、8083 WSS |

判障：设备连不上先查网络端口（nc 1883）、账号认证、clientid 唯一（重复 clientid 会互踢）；连得上无数据查订阅关系、主题前缀（electric/voltage 等）、ACL 授权与 QoS。

### 4.5 TDengine（3.2.0.0 / 3.3.6.13；6030 原生、6041 REST；库 energy，用户 energy）

```bash
# 连接（-p 与密码间无空格）
docker exec -it zhurong-ems-tdengine taos -u root -pdifyai123456
SHOW DATABASES;
USE energy; SHOW STABLES; SHOW TABLES;
SELECT COUNT(*) FROM hospital_device_data;
SELECT LAST_ROW(ts) FROM hospital_device_data;        -- 最新数据时间
SHOW TRANSACTIONS;
-- 保留策略（建库时 KEEP/DURATION；3.3.6 调整示例）
ALTER DATABASE energy KEEP 365;
ALTER DATABASE energy DURATION 10;
-- 连接检查（REST，后端 JDBC-RS 使用 6041）
curl -u root:<pwd> http://localhost:6041/rest/sql -d 'show databases'
```

要点：

- 后端通过 RESTful 驱动连接：`jdbc:TAOS-RS://<host>:6041/energy?user=energy&password=...&timezone=Asia/Shanghai`；
- 3.3.6.13 密码须满足大小写+数字/特殊复杂度；不支持 `CREATE USER IF NOT EXISTS`；不要用 `TAOS_ROOT_PASSWORD` 覆盖；不要给容器加自定义 command；
- `value` 是保留字，数值列用 `metric_value`；历史对象重命名脚本 `数据库脚本/hospital_rename_reserved_words.sql`；
- 数据按时间自动过期（KEEP），扩容以磁盘与 VGROUP 为主，不要手工删除历史数据文件。

## 5 日志管理

### 5.1 日志路径与保留

| 日志 | 路径 | 保留/级别 |
|---|---|---|
| 后端全量/信息/错误 | logback 默认 `/home/aaprojects/autoee-ems/springboot/logs/sys-console.log`、`sys-info.log`、`sys-error.log`；建议覆盖到 `/data/ems/logs/backend/` | console 1 天、info/error 5 天，按天滚动 |
| systemd 包装输出 | `/data/ems/logs/backend/systemd.out.log`、`systemd.err.log` | 由 logrotate 管理，建议 30 天 |
| 54 容器后端 | 宿主 `/home/inspur/xuhz/docker/dockerdata/zhurong-ems-backend-logs` | 随卷持久化 |
| Nginx | `/var/log/nginx/ems_access.log`、`ems_error.log`；容器卷 `.../zhurong-ems-frontend-logs` | logrotate 30 天 |
| MySQL | 容器内 `/var/lib/mysql/*-slow.log`、error log | 慢日志按需开启，按月清理 |
| EMQX | 容器卷 `.../zhurong-ems-emqx-log`（/opt/emqx/log） | 控制台默认 10MB×5 |
| TDengine | 容器卷 `.../zhurong-ems-tdengine-log`（/var/log/taos） | 随容器策略 |
| XXL-Job 执行器 | 后端 `./logs/xxl-job`，保留 30 天 | 调度中心日志卷 54 已挂载 |
| simulator | `simulator/logs/mqtt_simulator.log`，10MB×5 | 联调用 |

logrotate 示例（`/etc/logrotate.d/zhurong-ems`）：

```
/data/ems/logs/backend/*.log /var/log/nginx/ems_*.log {
    daily
    rotate 30
    missingok
    notifempty
    compress
    delaycompress
    sharedscripts
    postrotate
        /bin/kill -USR1 $(cat /run/nginx.pid 2>/dev/null) 2>/dev/null || true
    endscript
}
```

### 5.2 日志级别（按 profile）

- local/dev：`com.zhurong-ems=debug`，可临时开启 p6spy 打印 SQL；
- prod/docker：root=INFO、`com.zhurong-ems=info`、`com.baomidou=WARN`、`org.springframework=WARN`；`spring.datasource.dynamic.p6spy=false`；
- 在线调整：actuator 暴露时可用 `logging.level.com.zhurong-ems` 端点（如已开放且做了访问控制），或重启时加 `--logging.level.com.zhurong-ems=debug` 临时排障，结束后立即恢复。

日志排障常用：

```bash
grep -n "Exception\|ERROR" /data/ems/logs/backend/sys-error.log | tail -50
grep -C 5 "InaccessibleObjectException" /data/ems/logs/backend/sys-console.log
# 按 trace 时间点取上下文
sed -n '/2026-09-14 10:20/,/2026-09-14 10:25/p' /data/ems/logs/backend/sys-console.log
docker logs --since 30m zhurong-ems-backend 2>&1 | grep -i tdengine
```

## 6 监控体系

| 层级 | 手段 | 关注内容 |
|---|---|---|
| 主机 | `node_exporter`（可选）/云监控/Zabbix | CPU、内存、磁盘、网络、时钟偏移 |
| 容器 | docker healthcheck + `docker stats`；推荐 cAdvisor/Prometheus | 重启次数、health、资源占用、卷磁盘 |
| JVM/应用 | Spring Boot Admin（54：http://IP:8690/admin，admin/zhurong123 改密）；actuator `/autoee-iot-ems/actuator/health,info,metrics` | 堆/元空间、GC、线程、数据源、健康明细 |
| 平台内置 | 系统监控页：服务监控、缓存监控（Redis）、在线用户、操作日志、登录日志 | CPU/内存/JVM/磁盘、Redis 命中率、会话、审计 |
| 调度 | XXL-Job 控制台（http://IP:9110/xxl-job-admin） | 调度日志、失败告警、执行器在线 |
| MQ | RabbitMQ 管理台 / EMQX Dashboard | 队列堆积、消费速率、设备在线、认证失败 |
| 业务 | 设备在线数、最新数据时间、回调成功率、报警量 | 30 分钟无数据即离线（monitor-offline-minutes=30） |

告警建议阈值（初值，按基线调整）：

| 指标 | 阈值 | 级别 |
|---|---|---|
| 主机磁盘 | > 85% 警告 / > 92% 严重 | P2/P1 |
| 内存/Swap | 使用 > 90% 持续 10 分钟 | P2 |
| 后端 health | 非 UP 连续 3 次（1 分钟/次） | P1 |
| MySQL 连接数 | > max_connections 80% | P2 |
| Redis | used_memory > maxmemory 90%、evicted 激增 | P2 |
| RabbitMQ | 任意业务队列 ready > 5000 或 10 分钟增长不消 | P2 |
| EMQX | 设备在线数同比下降 > 30% | P2 |
| TDengine | REST 6041 探测失败连续 3 次、磁盘 > 85% | P2 |
| 回调 | 5 分钟内非 200 比例 > 5% | P2 |
| XXL-Job | 任务连续失败 3 次 | P3 |
| 证书 | 有效期 < 30 天 | P3 |

## 7 数据备份与恢复

### 7.1 备份策略总表

| 对象 | 方式 | 周期 | 保留 | 存储 |
|---|---|---|---|---|
| MySQL autoee_ems | mysqldump 全量 + binlog 增量 | 每日 02:00 全量；binlog 实时保留 | 全量 30 天，月末全量 12 个月 | 本机 + 异机/对象存储 |
| MySQL xxl_job | mysqldump | 每日随全量 | 30 天 | 同上 |
| Redis | RDB 快照（bgsave 拷卷）+ 配置备份 | 每日 | 7 天 | 异机 |
| TDengine | taosdump 逻辑备份（或快照） | 每周；全量每月 | 90 天（时序可重建，按客户要求） | 异机 |
| Nginx/应用配置 | conf、application-override、compose（不含 54 原文件） | 每次变更后 + 每周 | 永久版本化 | Git/文件服务器 |
| Docker 卷 | 卷级快照/目录打包（升级前必做） | 变更前 | 至下次稳定版本 | 异机 |

## 8 账号与安全运维

1. **密码信封**：所有中间件/系统口令密封交客户留存，运维不得在 IM/邮件明文传递；每 90 天轮换或按客户制度执行。
2. **账号季度复核**：MySQL `SELECT user,host FROM mysql.user;`、RabbitMQ `rabbitmqctl list_users`、EMQX Dashboard 用户与内置库认证用户、平台 `sys_user`、Linux `/etc/passwd` 与 sudoers；清理离职/僵尸账号。
3. **最小权限**：应用账号禁止 ALL ON *.*；MySQL 仅 autoee_ems 所需 DML；TDengine 仅 energy 库 GRANT；EMQX 设备账号限定主题；RabbitMQ 限定 admin_vhost。
4. **审计**：平台操作日志 sys_oper_log、登录日志 sys_logininfor 定期导出归档；Nginx access log 保留 30 天；异常时段（大批量导出、非工作时间登录）每周抽查。
5. **时钟**：所有节点 chrony 同步，`chronyc tracking` 核对；时钟漂移直接导致 IOT 回调 HMAC 签名失败。
6. **漏洞与证书**：月度补丁评估；镜像基础镜像（nginx/alpine/ubuntu）随版本更新；HTTPS/MQTTS 证书到期前 30 天更换。

## 9 常见故障处理 SOP

> 通用第一步：保留现场（截图、日志、时间点）→ 定位层级（网络/容器/中间件/应用/数据）→ 按 SOP 处置 → 记录工单。重启不是首选，重启前先抓日志与状态。

### 9.1 全站 500，日志含 InaccessibleObjectException（JDK 兼容）

| 项 | 内容 |
|---|---|
| 现象 | 所有页面/接口 500，后端日志 `java.lang.reflect.InaccessibleObjectException`、CGLIB/反射访问 ClassLoader 失败 |
| 原因 | 使用 JDK 9+（17/21）启动但缺少 `--add-opens`；本项目强制 JDK 1.8 |
| 排查 | `java -version`；`ps -ef \| grep zhurong-ems-admin.jar` 看参数；grep 异常栈 |
| 解决 | 首选切换 JDK 1.8 重启；不能切换时补齐 10 项 `--add-opens`（java.base 的 java.lang、java.lang.reflect、java.math、java.util、java.util.concurrent、java.net、java.io、java.nio、sun.nio.ch、sun.security.ssl 全部 =ALL-UNNAMED），详见 05-01 第 7.2 节；容器镜像检查 JAVA_OPTS 是否含全部 10 项 |

### 9.2 特定模块 500：数据库表缺失

| 项 | 内容 |
|---|---|
| 现象 | 仅打开某菜单/某功能 500，日志 `Table 'autoee_ems.xxx' doesn't exist` |
| 原因 | 脚本未导入或导入顺序遗漏 |
| 排查 | `SHOW TABLES LIKE 'xxx';`；对照 `.dev/dumps/ems_full.sql` 中 DDL；医院对象查 `数据库脚本/hospital_init.sql` |
| 解决 | 从 ems_full.sql 提取该表 DDL 在生产执行（或补导对应加性脚本）；执行后重启不需要（MyBatis 无表缓存），复测功能；补导前备份并核对字符集 utf8mb4 |

### 9.3 Redis 认证错误

| 项 | 内容 |
|---|---|
| 现象 | 后端启动/运行报 `NOAUTH Authentication required`、`WRONGPASS invalid username-password pair` |
| 原因 | Redis 设了 requirepass 但后端未配/配错；shared-redis 未以 `--requirepass difyai123456` 启动；改密后未同步 |
| 排查 | `redis-cli -a <pwd> ping`；核对 application-{profile}.yml 的 spring.redis.password 与 redis.conf；`CONFIG GET requirepass` |
| 解决 | 三处对齐（服务端口令、后端 spring.redis、Redisson 配置），重启后端；shared 形态必须带 `--requirepass difyai123456` |

### 9.4 RabbitMQ vhost/权限问题

| 项 | 内容 |
|---|---|
| 现象 | `connection refused`、`ACCESS_REFUSED`、`NOT_ALLOWED - vhost admin_vhost not found` |
| 原因 | profile 间账号/vhost 不一致（local 用 rabbitmq/rabbitmqpassword@admin_vhost，自研 compose 默认 guest@/）；用户未对 vhost 授权 |
| 排查 | `rabbitmqctl list_vhosts`、`list_users`、`list_permissions -p admin_vhost`；管理台 Queues 看消费者 |
| 解决 | 建 vhost/用户并 `set_permissions -p admin_vhost <user> '.*' '.*' '.*'`；后端配置同步后重启；核对 5672 安全组 |

### 9.5 EMQX 连不上 / 连上无数据

| 项 | 内容 |
|---|---|
| 现象 | 设备/后端 MQTT 连接失败；或在线但平台无数据 |
| 原因 | 1883 不通；账号认证失败；clientid 重复互踢；ACL 拒绝；主题不匹配；后端订阅未建立 |
| 排查 | `nc -vz IP 1883`；Dashboard 客户端/认证日志/订阅；后端日志 mqtt 关键字；simulator 配置 host/账号 |
| 解决 | 开通端口；在内置 DB 认证中建账号并核对密码；clientid 全局唯一（后端为 zhurong-ems-server-<HOSTNAME>）；授权 publish/subscribe 主题；主题对齐 electric/#、water/#；重启后端消费者并在 Dashboard 确认订阅 |

### 9.6 TDengine 初始化失败 / 保留字报错

| 项 | 内容 |
|---|---|
| 现象 | 容器启动初始化报错、`syntax error near "IF NOT EXISTS"`、`invalid identifier: value`、Authentication failure |
| 原因 | 挂载 init.sql 只在首次空卷执行；3.x 不支持 `CREATE USER IF NOT EXISTS ... WITH PASSWORD`；3.3.6.13 密码复杂度不满足；`value` 保留字；`-p` 后加了空格 |
| 解决 | 手动初始化：`CREATE DATABASE IF NOT EXISTS energy;` → `CREATE USER energy PASS '复杂口令';`（已存在先 SHOW USERS，报 User already exists 跳过）→ `GRANT ALL ON energy TO energy;`；复杂口令含大小写+数字/特殊；不使用 TAOS_ROOT_PASSWORD、不自定义 command；列名用 metric_value（执行 hospital_rename_reserved_words.sql 处理历史对象）；CLI 写法 `-pdifyai123456` 无空格。详见 [TDengine 手动初始化操作手册](../部署指南/TDengine%20手动初始化操作手册.md) |

### 9.7 消息堆积 / 频繁 basicNack

| 项 | 内容 |
|---|---|
| 现象 | RabbitMQ 队列 ready/unacked 持续升高，页面数据延迟 |
| 原因 | 消费者宕机；消费抛异常重回队列；下游 DB 慢/锁；突发压测流量；QoS 太高 |
| 排查 | `list_queues ... consumers/messages`；后端 sys-error.log；MySQL processlist/慢查询；EMQX 消息速率 |
| 解决 | 恢复消费者；修复消费异常（脏数据隔离到死信队列，避免无限重投）；优化慢 SQL/扩连接池；限流压测；恢复后观察队列清零速率 |

### 9.8 医院 IOT 回调 401 / 签名失败

| 项 | 内容 |
|---|---|
| 现象 | IOT 平台推送返回 401/失败，或平台日志 token/sign/IP 校验不通过 |
| 原因 | X-IOT-Token 不一致（默认 hospital-iot-2026，两端必须相同）；开启签名后 X-IOT-Sign 算法/密钥不一致；时钟漂移；出口 IP 不在 ip-whitelist；Nginx 未传 X-Forwarded-For |
| 排查 | 后端回调日志 `HospitalCallback`；`date` 对比两端时间；`curl` 模拟（见 05-01 10.3）；管理台回调日志页面 |
| 解决 | 同步 token；按 hex(HMAC_SHA256(secret, timestamp+"\n"+msgId)) 修正签名并配置 sign-secret；chronyc 校时；白名单加入真实出口 IP（多级代理取首 IP）；Nginx 透传代理头；路径 POST /autoee-iot-ems/hospital/callback/data |

### 9.9 前端 404 / 接口 502

| 项 | 内容 |
|---|---|
| 现象 | 页面 404、刷新子路由 404；接口 502 Bad Gateway |
| 原因 | dist 未部署到 root；缺 `try_files $uri $uri/ /index.html`；后端未启动/端口不通；proxy_pass upstream 名错；容器网络不通 |
| 排查 | `curl -I http://localhost/`；`curl http://localhost/autoee-iot-ems/actuator/health`；`nginx -t`；ems_error.log；`docker network`/防火墙 |
| 解决 | 校正 root 指向 dist；补 SPA fallback；先恢复 8088 后端；proxy_pass 指向正确 upstream（裸机 http://127.0.0.1:8088/autoee-iot-ems/，容器 http://zhurong-ems-backend:8088/autoee-iot-ems/）；同网络/放行端口后 reload |

### 9.10 磁盘满

| 项 | 内容 |
|---|---|
| 现象 | 写入失败、MySQL 报错、容器只读/重启、日志中断 |
| 原因 | 数据盘增长、binlog/慢日志/容器日志（json-file 无限增长）、备份堆积 |
| 排查 | `df -h`；`du -sh /data/* /var/lib/docker/containers/* | sort -h | tail`；`docker system df` |
| 解决 | 紧急：清理过期备份、`PURGE BINARY LOGS BEFORE '...'`、`docker logs` 容器日志 truncate；根治：logrotate、`/etc/docker/daemon.json` 配 log-opents max-size=100m/max-file=3、binlog_expire_logs_seconds、扩容数据盘 |

### 9.11 时钟漂移导致签名/数据异常

| 项 | 内容 |
|---|---|
| 现象 | 回调签名间歇失败、设备数据时间偏移、调度不准时 |
| 原因 | NTP 未配置/失效 |
| 排查 | `timedatectl`；`chronyc tracking`；各容器 `date`（TZ=Asia/Shanghai） |
| 解决 | 启用 chronyd 同步内网/公网 NTP，强制 makestep；容器依赖宿主时钟并确认 TZ 变量；校时后复测签名 |

### 9.12 其他高发速查

| 现象 | 关键点 |
|---|---|
| 登录页验证码出不来 | 后端 500（查 9.1/9.2）；Nginx /prod-api 代理错误；Redis 不通 |
| 菜单不显示/菜单乱码 | hospital_menu 系列未导全；连接字符集非 utf8mb4；执行 `fix_sys_menu_encoding.sql`；角色授权 |
| XXL-Job 执行器不在线 | access-token 不一致（default_token）、admin-addresses 不通、执行器 9101 端口被占 |
| 报表导出失败 | temp/上传目录不可写或磁盘满；`ruoyi.profile`、multipart.location 路径不对 |
| EMQX Dashboard 无法登录 | admin/public 首登强制改密后遗忘；通过 `emqx ctl admins passwd admin <new>` 重置 |
| 容器不断重启 | `docker logs <名>` 看退出原因；多为依赖未 healthy/口令错误/端口冲突；`docker compose down && up -d` 前先查配置 |

## 10 性能调优

### 10.1 JVM

- 堆：单体建议 `-Xms` 与 `-Xmx` 设同值避免动态扩缩（4G 机器 1g/2g，8G 机器 2g/4g），元空间 128m/256m；
- GC：JDK 8 可用 `-XX:+UseG1GC -XX:MaxGCPauseMillis=200`；避免在容器内超出限制（配合 `-XX:MaxRAMPercentage=75.0`）；
- 持续监控 GC 频次与停顿（Spring Boot Admin），Full GC 频繁时 dump 堆（`-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/ems/logs/heap`）后分析。

### 10.2 MySQL 与连接池

- HikariCP：docker profile 默认 minimum-idle=10、maximum-pool-size=100；prod yml 默认 maxPoolSize=20/minIdle=10。按实例规格与 Pod/实例数反推：`连接池总和 ≈ max_connections(1000) 的 70% 以内`；
- 索引：每月分析慢查询 TOP SQL，补齐 where/join/order by 复合索引；避免对雪花 ID 外索引字段用函数；
- 表数据量大的设备时序明细应入 TDengine，MySQL 只存业务/聚合数据；
- 参数：innodb_buffer_pool_size 建议物理内存 50%~60%（独立 DB 节点）；开启慢查询 long_query_time=1~2s。

### 10.3 Undertow / 接口层

- 配置基线：IO 线程 8、worker 256、buffer-size=512、direct-buffers=true（application.yml 已内置）；高并发可按 `worker ≈ 核数×32~256` 调整并压测验证；
- 设备高峰在接入层（EMQX/消费侧）横向扩展，不盲目调大 HTTP worker；
- Nginx：开 gzip/gzip_static、静态资源强缓存、`proxy_buffering off` 仅对实时/SSE 接口保留；开启 `keepalive` 到 upstream。

### 10.4 必须关闭的开发期组件

- `spring.datasource.dynamic.p6spy=false`（生产/docker profile 默认 false，发布前复核）；
- MyBatis `logImpl` 的 StdOutImpl SQL 直印在生产调回 Slf4j 或关闭；
- devtools 热部署不打入生产启动；springdoc/swagger 公网关闭。

### 10.5 压测工具

simulator 内置轻/中/重三档（10 设备 1 msg/s → 1000 设备 10 msg/s），正式压测前通知 DBA 并在低峰执行，压测数据需可识别（测试设备编码前缀 TEST-）并在结束后清理。

## 11 变更发布流程与窗口

1. **申请**：提交变更单（内容、影响、窗口、回退方案、责任人），客户审批；

4. **发布**：按 05-03 第 3 章步骤执行（备份→部署→脚本→配置→冒烟→放量），一人操作一人复核并记录时间点；
5. **发布后**：观察 30~60 分钟核心指标，更新文档/密码/监控，关闭变更单；
6. **纪律**：禁止手工改生产代码与 54 编排脚本；禁止未备份执行 DDL；SQL 先在预发执行；回退决策时限不晚于窗口结束前 60 分钟。

## 12 扩容方案

| 瓶颈 | 判据 | 扩容手段 |
|---|---|---|
| 后端 CPU/连接打满 | CPU > 80%、RT 上升、health 抖动 | 无状态水平扩容：增后端实例 + Nginx upstream 负载；注意 Sa-Token 会话共享 Redis、MQTT clientid 唯一、XXL-Job 执行器多实例 |
| MySQL 算力 | 连接数长期 80%、慢查询无法再优化 | 升配（vCPU/内存/SSD）→ 读写分离（动态数据源加 slave）→ 冷热分离/归档 |
| MySQL 容量 | 数据盘 > 80% | 扩盘；设备明细迁移 TDengine；历史表分区/归档 |
| Redis | 内存达 maxmemory、命中率下降 | 调大 maxmemory/升配；key 治理；后续可哨兵/集群 |
| RabbitMQ | 消费持续滞后 | 增加消费者实例/并发；队列分流；镜像/仲裁队列规划 |
| EMQX | 连接数/吞吐达单机上限 | EMQX 集群 + LB 透传 MQTT；按 topic/节点分组 |
| TDengine | 写入/磁盘瓶颈 | 加节点扩 vgroup、KEEP 缩短、独立磁盘；taosdump 归档冷数据 |
| Nginx | 带宽/连接瓶颈 | LB/多实例前置 SLB；静态资源 CDN/对象存储 |
| 磁盘 | 全线增长 | 数据盘在线扩容 + 日志/备份生命周期治理 |

扩容后必须回归：设备一条数据闭环、回调 200、报表导出、调度任务、监控采集。
