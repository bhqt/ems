## 3 上线实施步骤（含命令与负责人）

### 3.1 冻结与备份（DBA/运维）

```bash
# 1) 记录当前位点与版本
docker exec zhurong-ems-mysql mysql -uroot -p<pwd> -e "SHOW MASTER STATUS;"
docker exec zhurong-ems-mysql mysql -uroot -p<pwd> -e "SELECT VERSION();"
docker images | grep zhurong-ems
# 2) 全量备份
mkdir -p /data/backup/preonline
docker exec zhurong-ems-mysql mysqldump -uroot -p<pwd> \
  --single-transaction --routines --triggers --events \
  --default-character-set=utf8mb4 --set-gtid-purged=OFF autoee_ems \
  | gzip > /data/backup/preonline/autoee_ems_$(date +%F_%H%M).sql.gz
gzip -t /data/backup/preonline/autoee_ems_*.sql.gz && echo BACKUP_OK
# 3) 配置与卷备份（54 脚本只读，备份应用配置/日志目录）
tar czf /data/backup/preonline/conf_$(date +%F_%H%M).tar.gz \
  /opt/zhurong-ems/backend/application-override.yml /opt/zhurong-ems/nginx 2>/dev/null || true
```

## 5 回滚触发条件与决策分级

### 5.1 触发条件（满足任一即进入回滚评估）

1. 冒烟 P0 用例失败且 30 分钟内无法修复；
2. 后端 health 非 UP、持续重启、或出现大面积 500（错误率 > 5%）；
3. MQTT 主链路中断、设备数据大面积不入账（在线数骤降 > 30%）；
4. 医院 IOT 回调持续失败、影响对端业务；
5. 数据库脚本执行失败导致核心表结构/数据损坏且无法快速修正；
6. 服务器资源耗尽（磁盘满、OOM）导致服务不可用；
7. 出现数据错乱、误删数据等数据安全事件；
8. 客户业务方要求停止放量。

### 5.2 决策分级

| 等级 | 情形 | 决策人 | 动作 |
|---|---|---|---|
| L1 局部回退 | 单组件/单节点异常，摘流重启可恢复 | 实施负责人 | 摘该节点/重启，继续观察，不整体回退 |
| L2 版本回退 | 新版本功能性故障，旧版本确认可用 | 上线指挥（客户确认） | 执行第 6 章应用回滚（前端/后端），数据库原则不动 |
| L3 数据回退 | 脚本破坏数据/错误数据已扩散 | 上线指挥 + DBA + 开发 | 备份恢复/PITR + 消息补偿（第 6.3、7 章） |
| L4 灾难恢复 | 主机/存储级故障 | 应急小组 | 启用备用节点，按灾难恢复预案重建 |

回退决策时限：不晚于窗口结束前 60 分钟；一旦决定回退，20 分钟内完成应用层回退并恢复业务，数据层处置并行推进。

## 6 回滚步骤

### 6.1 后端回滚

裸机 jar：

```bash
# Nginx 先摘流（权重置 0），等待存量请求结束
systemctl stop zhurong-ems
cp /opt/zhurong-ems/backend/zhurong-ems-admin.jar.bak /opt/zhurong-ems/backend/zhurong-ems-admin.jar
# 确认启动脚本/覆盖配置为旧版本兼容值（profile/td 开关）
systemctl start zhurong-ems
sleep 20
curl -s http://localhost:8088/autoee-iot-ems/actuator/health
```

容器（54 脚本不改，用旧 tag/旧镜像）：

```bash
# 若编排固定 latest：重新打回旧镜像 tag
docker tag zhurong-ems/backend:<旧版本tag> zhurong-ems/backend:latest
docker compose -f docker-compose-54.yml up -d --no-deps zhurong-ems-backend
docker image inspect zhurong-ems/backend:latest   # 确认镜像 ID 为旧版本
curl -s http://localhost:1088/autoee-iot-ems/actuator/health
```

### 6.2 前端回滚

```bash
# 裸机
rm -rf /opt/zhurong-ems/frontend/dist
mv /opt/zhurong-ems/frontend/dist.bak.<时间戳> /opt/zhurong-ems/frontend/dist
nginx -t && systemctl reload nginx
# 容器
docker tag zhurong-ems/frontend:<旧版本tag> zhurong-ems/frontend:latest
docker compose -f docker-compose-54.yml up -d --no-deps zhurong-ems-frontend
# 通知用户强刷/Ctrl+F5（旧 index.html 可能被浏览器缓存，静态资源文件名带 hash 不冲突）
```

### 6.3 数据库回滚

- **加性脚本**（本项目医院系列均为 `CREATE TABLE IF NOT EXISTS`/菜单 INSERT 加性）：旧版本对新表/新菜单无引用，应用回滚后**通常无需回退结构**；确需移除新菜单时执行预先评审的反向 DELETE（按 menu_id 段 1979000000000000001 段精确删除），表可保留不删，避免风险；
- **破坏性/数据修改类脚本**：
  1. 优先在窗口内用预演通过的反向脚本修复；
  2. 无法反向修复时，在独立临时库恢复 T 日 09:00 全量备份 → 应用 binlog 重放到故障前位点 → 核对后将受影响表导出合并回生产（单表可 `RENAME TABLE` 切换）；
  3. 全库恢复为最后手段：停应用 → 恢复全量 → 追平 binlog → 启动旧版本；
- 全程禁止在生产直接做无备份的 DROP/TRUNCATE；所有 SQL 双人复核。

### 6.4 中间件回滚

- 中间件本次原则上**只加账号不改结构**：新增的 vhost/账号/主题规则保留不影响旧版；确认有影响的按操作记录反向删除（`rabbitmqctl delete_user/vhost`、EMQX 禁用规则）；
- 镜像升级失败：停新容器 → `docker compose up -d` 用原镜像 tag 重建；卷不删除；
- TDengine：应用回滚后把 `td.enabled=false` 即可完全旁路；库内数据保留不动（时序追加型，无需回退）。

### 6.5 回滚验证

| 验证项 | 标准 |
|---|---|
| 后端 health | UP，启动日志无 ERROR |
| 前端 | 登录/首页/设备列表正常，版本为旧版 |
| MQTT 闭环 | 一条测试数据到库到页面 |
| 回调 | IOT 方推送 200 |
| 队列 | RabbitMQ 无异常堆积，消费者在线 |
| XXL-Job | 执行器在线、任务恢复调度 |
| 数据 | 核对关键表记录数与回滚前备份一致/符合预期 |

回滚完成后由指挥宣布恢复服务，留存全部时间线，24 小时内召开复盘会，问题修复后重新走上线流程。

## 7 数据回滚与消息补偿特别说明

### 7.1 TDengine

- 时序数据只追加、按 KEEP 自动过期，**不做数据回退**；应用层回滚后关闭 td 数据源（`td.enabled=false`）即与旧版完全兼容；
- 若新版本写入过错误数据点：用时间范围+TAG 条件精准删除（`DELETE FROM energy.hospital_device_data WHERE ...`），删除前先 `SELECT COUNT(*)` 圈定并记录；禁止删库删表。

### 7.2 MySQL

- 回滚窗口内停止消费/写入（后端停服）后再做数据修复，避免边恢复边写；
- 业务主键为雪花 ID，恢复合并时不得重置自增序列；
- 菜单/配置类误数据按主键精确 DELETE/UPDATE，先 SELECT 后写，事务内执行并留存语句；
- binlog 恢复操作在临时库完成校验后才允许作用于生产。

### 7.3 RabbitMQ 消息补偿

1. **不清理队列**：回滚期间消息继续堆积在 `hospital.device.data.queue` 等队列，旧版消费者启动后自动续消费；回滚前确认队列无消息 TTL/死信丢弃策略会丢消息；
2. **重复消费处理**：回滚/重投可能造成重复，消费侧按 msgId/设备时间点幂等；无幂等保证的，导出堆积消息与库内记录按 msgId 对账去重；
3. **死信/失败消息**：从死信队列导出，人工或脚本修正后重投，重投脚本须经开发评审，先灰度 10 条；
4. **IOT 回调补偿**：与 IOT 方约定失败重试窗口，回滚后请对方按 msgId 重推失败时段数据；平台回调日志（HospitalCallbackLog）列出非 200 清单作为补偿依据；
5. **MQTT 补偿**：MQTT 无持久离线保证的消息不补发——以 MySQL/TDengine 中最后一条数据时间为准，协调设备侧补报该时段数据，或由 simulator/补数脚本按分钟粒度补采。
