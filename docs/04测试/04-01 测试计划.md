## 1 测试目的与范围

### 1.1 测试目的

1. 验证 V4.6.0 在加性叠加"医院智慧能源决策系统"后，**原有 EMS 全部功能不退化、性能不劣化、数据不丢失**。
2. 验证医院模块外部 IOT 平台 HTTP 回调接入、报文解析、RabbitMQ 异步落库、检查检验设备台账与能效分析、医院报警、医院大屏等增量功能满足需求与设计要求。
3. 验证 MQTT 直采与 IOT HTTP 回调两条采集链路在正常、异常、高并发、断网恢复等场景下的正确性与可靠性。
4. 验证非功能指标达成：**回调吞吐 ≥ 1000 TPS、普通查询 P95 ≤ 1s、大屏首屏 ≤ 3s、核心链路可用性 ≥ 99.9%、回调失败可重试不丢数据**。
5. 输出可追溯的测试证据与质量结论，为 V4.6.0 上线提供放行依据。

### 1.2 加性开发回归原则

本次为 RuoYi 二开平台上的**加性（叠加式）开发**，测试遵循以下原则：

| 原则 | 说明 |
| --- | --- |
| 原功能全量回归 | 设备/网关、能耗分析、报警、运维巡检、物品危化品、定额、充电桩、碳资产、视频、数据查询、管理体系、计量、新能源、水务、调度预测、数字孪生、集控、报表引擎、系统集成、系统管理、系统监控等原有模块执行全量功能回归 |
| 共享组件重点回归 | 对 Sa-Token 鉴权、动态菜单、字典、代码生成、文件服务、消息中心、MyBatis-Plus 基础配置、MQTT→RabbitMQ→存储公共链路执行重点回归 |
| 新增独立验证 | 医院模块（回调接入、台账、指标、院区分区、实时监测、能效、节能建议、报警、大屏、中英文）作为增量独立设计与执行测试 |
| 交叉影响分析 | 医院模块对公共 MQ 消费器 `MyAckReceiver`、报警规则引擎、TDengine 写入层、网关路由的改动点必须做影响面分析并专项回归 |
| 配置开关双态验证 | TDengine 启用/关闭（`spring.datasource.dynamic.datasource.td.enabled`）两种模式均须通过回归 |

## 3 测试策略与类型

### 3.1 总体策略

采用 **V 模型 + 迭代测试**：每个里程碑（M1~M4）执行"单元→接口→集成→系统"分层测试，里程碑末做增量回归；M4 执行全量系统回归、非功能专项与验收测试。缺陷管理与准出标准贯穿全程，详见 [04-03 缺陷管理与测试报告规范.md](04-03%20缺陷管理与测试报告规范.md)。

### 3.3 测试暂停与恢复

- 出现 S1 致命缺陷（服务不可启动、数据丢失、回调全量失败）时暂停本轮测试，挂起相关用例，发《测试暂停通知》。
- 阻断缺陷修复并通过冒烟后恢复，已执行用例结果保持有效，仅回归影响面。

## 8 测试数据方案

### 8.1 数据来源与用途

| 数据/工具 | 路径 | 用途 |
| --- | --- | --- |
| 全量结构与基础数据 | `.dev/dumps/ems_full.sql` | 初始化 autoee_ems，校验表完整性 |
| 医院演示种子数据 | `数据库脚本/hospital_seed_demo.sql` | 院区分区、设备台账、指标、规则演示数据 |
| MQTT 模拟器 | `simulator/main.py`（Python） | 单设备发送与压力测试；覆盖 electric/water 各 TopicType（U/I/P/W） |
| 模拟器配置 | `simulator/config/config.yaml`、`config/templates.yaml` | 设备模板、发送频率、压测参数 |
| 回调造数 | curl/Postman 脚本 | 构造医院 IOT 回调报文、错误 Token、错误签名、重放、批量、缺字段、乱序时间戳 |
| 业务造数 | SQL 脚本 + 页面操作 | 能耗、定额、工单、出入库、充电桩订单、价格策略计费等 |
| 监控数据 | Spring Boot Admin / XXL-Job 控制台 | 任务执行、服务健康取证 |

### 8.2 数据策略

1. 每轮测试前保存基线快照（MySQL dump + 必要的 TDengine 库导出），支持 30 分钟内还原。
2. 医院设备台账覆盖 CT、MRI、DR、超声、检验流水线、DSA 六类，每类至少 2 台并分布在 2 个以上院区。
3. 压测数据使用独立设备编码前缀（如 `STRESS_`），与功能数据隔离，压测后清理。
4. 时间戳数据覆盖：正常时间、未来时间、历史时间、乱序、重复、毫秒/秒级时间戳。
5. 质量戳数据覆盖：good/bad/uncertain 三种。
6. **数据脱敏**：类生产环境严禁使用真实患者信息；医院侧提供的设备/科室名称按约定脱敏，账号密码、HMAC 密钥不入测试文档明文仓库。

## 9 性能测试方案

> 系统集成域历史性能基线见 [../测试用例/性能测试计划.md](../测试用例/性能测试计划.md)，本章为 V4.6.0 全量指标，医院回调为新增重点。

### 9.1 指标与验收阈值

| 编号 | 场景 | 指标 | 阈值 | 监控点 |
| --- | --- | --- | --- | --- |
| PERF-01 | 医院 IOT 回调写入 | 吞吐 | ≥ 1000 TPS（稳定 10 分钟） | 网关 QPS、消费者处理速率 |
| PERF-02 | 医院 IOT 回调写入 | 错误率 | ≤ 0.1%，且无数据丢失 | 回调日志、死信队列 |
| PERF-03 | 普通业务查询 | 响应时间 | P95 ≤ 1s | 后端 access log/APM |
| PERF-04 | 医院大屏首屏 | 首屏加载 | ≤ 3s | 浏览器 Performance/埋点 |
| PERF-05 | 核心链路可用性 | 可用性 | ≥ 99.9%（考核窗口） | Spring Boot Admin/拨测 |
| PERF-06 | MQTT 高并发上报 | 吞吐 | 按设计容量 1.2 倍峰值加压 10 分钟无丢失 | EMQX 消息数 vs 落库数 |
| PERF-07 | RabbitMQ 堆积 | 恢复能力 | 制造 10 万堆积后消费者可追平，无死信风暴 | 队列 depth、消费速率 |
| PERF-08 | TDengine 写入/查询 | 写入速率/查询耗时 | 满足 PERF-01 联动写入；典型时序查询 P95 ≤ 1s | TDengine 监控 |
| PERF-09 | 资源水位 | CPU/内存/堆 | 稳定期 CPU ≤ 75%，Full GC 无频繁增长 | VisualVM/Admin |

### 9.2 加压模型与工具

| 场景 | 工具 | 加压模型 |
| --- | --- | --- |
| 回调 TPS | curl 批量脚本/自研并发客户端（正确 HMAC 预签名） | 阶梯加压 200→500→800→1000→1200 TPS，每级 5 分钟；1000 TPS 稳定 10 分钟；再做 30 分钟耐久 |
| MQTT 上报 | `simulator/main.py` 压测模式（多设备模板） | 设备数 100→500→2000，发送频率递增，混合 U/I/P/W 四类 TopicType |
| MQ 堆积 | 暂停消费者 + simulator 灌量 | 灌入 10 万条后恢复消费者，观测追平时间与死信 |
| 查询性能 | JMeter 线程组 | 50/100/200 并发用户，混合能耗趋势、同环比、报警历史、医院实时监测查询 |
| 大屏 | 浏览器多实例 + 接口压测 | 10/30/50 块大屏同时打开，测首屏与自动刷新接口 |
| 故障注入 | 手工/脚本 | 压测中分别 Kill 消费者、停 TDengine、断网 60s、重启 RabbitMQ，验证不丢数与恢复 |

### 9.3 数据核对方法

- 发送端计数（simulator 报告/回调脚本计数）= EMQX 转发计数 = RabbitMQ 投递计数 = MySQL 落库计数（+ 预期死信计数）。
- 回调场景：回调成功响应数 + 明确拒绝数（鉴权失败）= 请求数；应入库报文全部可在 MySQL/TDengine 与回调日志中双向追溯。
- 每轮压测留存：压测脚本版本、参数、服务端日志、监控截图、计数对账表。

## 10 安全测试要点

> 详细方案与检查表引用 [../测试用例/安全测试计划.md](../测试用例/安全测试计划.md)，本章列出 V4.6.0 必测项。

| SEC-06 | 回调重放攻击 | 截获合法报文重复提交；nonce/时间窗校验 | 超时间窗或重复 nonce 被拒；幂等键不产生重复数据 |

| SEC-09 | XSS | 字典、备注、设备名、节能建议等处注入脚本 | 转义存储/渲染，不执行 |
| SEC-10 | 弱口令与策略 | admin/123456 默认口、弱口令、爆破、验证码绕过 | 强制改密策略（类生产）、失败锁定、验证码有效 |
